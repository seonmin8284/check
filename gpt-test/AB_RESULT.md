## 0. 2차에서 무엇이 잘못됐나

2차는 arm 당 **1회 실행**으로 A F1 0.950, B 0.877 을 보고하고 "A 채택"을
권고했다. 부트스트랩 CI `[+0.026, +0.125]` 도 붙였다. 그 CI 는 *행* 재표집
분산만 잡고 *파스* 재추출 분산은 잡지 못한다. `run_csv*.py` 에는 temperature 도
seed 도 없다 — 같은 프롬프트가 매번 다른 파스를 낸다.

arm 당 3~4회 돌려 그 분산을 실제로 쟀다.

## 2. A rep1 은 운이 좋았던 게 아니다

`A rep1 이 rep2·rep3 이상인 source: 8/8`. 독립 추출이라면 (1/3)⁸ ≈ **0.015%**.

| arm | rep1 이 최고인 source |
|---|---|
| A | **8/8** ← 그래프가 이 실행에 맞춰졌다 |
| B | 6/8 |
| C | 2/8 |

capability graph 의 EXPANSION 규칙들이 A rep1 의 파스를 보며 작성됐다. 코드에
흔적이 남아 있다 — `PRICE_GATE` 독스트링의 `invest/2 g2` 는 A rep1 의 출력이다.
C 의 rep1 편향이 2/8 인 것이 대조군 역할을 한다: `route_intent.py` 는 C 에
과적합돼 있지 않고, 그런데도 C 는 진다. **즉 C 의 열세는 측정 편향이 아니라
진짜 스키마 열세다.**

`ab_fit.py` 는 규칙 *선택*을 기계화해 이 편향을 걷으려 했지만, 규칙 *작성*의
편향은 걷지 못한다고 스스로 밝혀놨다. 그 잔여 편향의 크기가 이제 측정됐다 —
**약 +0.06 F1**.

## 4. C 는 단일로는 최악, 앙상블에서는 필수

C 의 열세는 어느 조건에서도 견딘다.

| 비교 | Δ | 부호검정 | 실행쌍 |
|---|---|---|---|
| A−C | +0.0712 | A27:C12, p=0.024 | 9/9 A 우세 |
| B−C | +0.0650 | B23:C9, p=0.020 | 9/9 B 우세 |

goal 분해(A/B)가 flat intent 분류(C)보다 **+0.07** 낫다. 스키마는 유지한다.

**그런데 C 를 버리면 안 된다.** §5 참조 — 앙상블 구성원으로서의 가치는 단일
성능과 무관하다.

## 5. 앙상블 — 같은 예산이면 반복보다 다양성

결손의 큰 몫이 "같은 arm 이 실행마다 다른 답을 낸" 행에 있다. 파스가 안정한
행은 F1 0.91~0.92, 흔들리는 행은 0.68~0.81 이다.

| arm | 파스 안정성 (신규추출 2회 동일) | 안정행 F1 | 불안정행 F1 |
|---|---|---|---|
| A | 72% | 0.921 (n=48) | 0.806 (n=19) |
| B | **84%** | 0.910 (n=56) | 0.683 (n=11) |
| C | 67% | 0.865 (n=45) | 0.705 (n=22) |

호출 예산을 고정하고 구성을 쓸었다 ([ensemble_sweep.py](ensemble_sweep.py), dev 45행,
rep1 제외):

| 예산 | 최적 구성 | F1 | P | R | 단일 대비 |
|---|---|---|---|---|---|
| 1회 | B 단일 | 0.8767 | 0.865 | 0.889 | — |
| 2회 | B×2 만장일치 | 0.8867 | 0.917 | 0.858 | +0.010 |
| **3회** | **A+B+C 다수결≥2** | **0.9101** | 0.915 | 0.906 | **+0.033** |

같은 3콜에서:

```
A+B+C 다수결≥2   0.9101   ← 서로 다른 프롬프트 한 번씩
B×3 만장일치      0.8966
B×3 다수결≥2     0.8688   ← 한 프롬프트 세 번
A×3 다수결≥2     0.8744
```

**한 프롬프트를 세 번 돌리는 것보다 다른 프롬프트를 한 번씩 돌리는 게 낫다.**
메커니즘은 오류 상관이다 — 오류 자카드가 같은 arm 0.632, 다른 arm 0.501.
같은 프롬프트는 같은 자리에서 같이 틀려 투표해도 상쇄가 안 된다.

배포: [ensemble_predict.py](ensemble_predict.py).

## 6. 프롬프트 결정성 작업 — 하지 않음

B 를 더 결정적으로 만드는 작업을 검토했고 **접었다.**

1. B 는 이미 `strict: true` json_schema 에 `domain`/`facet`/`horizon`/엔티티
   타입까지 enum 으로 묶여 있다. 스키마 제약 레버는 소진됐다.
2. B 의 dev 불안정은 **7행**이고 원인이 흩어져 있다 — goal 개수 2, domain·facet
   2, 엔티티 구성 2, 기타 1. 겨냥할 단일 레버가 없다.
3. **상한을 쟀다.** B 가 완벽히 결정적이 되어 항상 최빈 파스를 낸다면
   0.8767 → **0.8991 (+0.022)**. §5 의 앙상블이 이미 준 +0.033 보다 작고, 같은
   잡음을 원천으로 하므로 더해지지도 않는다.

## 7. 그래프 재적합 — 실행했으나 적용하지 않음

[refit_graph.py](refit_graph.py) 로 dev 45행에서만 재적합했다. 두 후보가 나왔고
**둘 다 기각했다.**

| 후보 | dev 이득 | 기각 사유 |
|---|---|---|
| `JUDGMENT_BUNDLE[('issuer','current')]` → `('get_stock_news',)` | +0.0105 | 이 자리가 걸리는 dev 행이 **1개**(invest/4) |
| 규칙 24개 → 17개 | +0.0000 | 제거된 7개 중 **5개가 dev 발화 0회** |

두 번째가 특히 중요하다. backward elimination 이 "빼도 안 나빠진다"고 판정한
규칙 중 다수는 **dev 에서 아예 발화하지 않는다.** 그건 무용하다는 증거가
아니라 증거가 없다는 뜻이고, 빼면 근거 없는 도박이다.

```
   0  non-equity index→industry channel           발화 0 — 증거 없음
   0  corporate_event on price→announcement+news  발화 0 — 증거 없음
   0  index-relative assessment→price             발화 0 — 증거 없음
   0  internal regulation→policy                  발화 0 — 증거 없음
   0  next-step→guide                             발화 0 — 증거 없음
   2  comparative assessment                      발화하나 점수 불변
   1  document→policy                             발화하나 점수 불변
```

**dev 45행으로는 24규칙 그래프를 더 맞출 수 없다.** 이게 결론이다.

## 9. 판단

> ⚠️ 판단 1·3 은 §11 에서 갱신됐다. 1 은 더 강해졌고(B 가 앞선다), 3 은
> 약해졌다(+0.0185 → +0.012).

1. **A 채택 근거 없음.** 2차의 "A 채택" 권고는 철회한다. 신규 추출에서 A−B 는
   +0.009, p=1.000 이다. 프롬프트 설계로는 두 안이 구분되지 않는다.
   → §11: 미노출 116행에서는 **B 가 +0.030 으로 앞선다.**
2. **단일 arm 을 골라야 한다면 B.** F1 이 같고 분산이 1/9, 파스 안정성이
   84% 대 72% 다. 같은 질의에 같은 함수를 부르는 쪽이 운영에 낫다.
3. **3콜을 쓸 수 있다면 A+B+C 다수결.** holdout 기준 +0.0185. C 는 단일로는
   최악이지만 오류가 덜 상관돼 있어 앙상블에서 값을 한다.
   → §11: 미노출 표본에서 **+0.012 로 축소.** 비용 대비 판단이 갈린다.
4. **그래프도 프롬프트도 지금 데이터로는 더 못 맞춘다.** 다음 개선은 규칙이나
   프롬프트가 아니라 **골든 확장**에서 나와야 한다.
   → §11: 골든이 273행이 되면서 이 조건이 해소됐다. 재적합이 가능해졌다.

## 10. 한계

- **holdout 이 진짜 처녀지가 아니다.** 동결이 3차 측정 시점에 이뤄졌고,
  그래프와 프롬프트는 그 전에 67행 전체를 보며 만들어졌다. +0.0185 는 *동결
  이후 내린 결정(앙상블)* 에 대해 유효하지만, **0.8625 를 일반화 성능으로
  읽으면 여전히 낙관적이다.**
- **holdout 은 소진됐다.** 다음 라운드는 새로 잘라야 한다.
- **22행은 작다.** holdout 의 ±1행이 F1 을 0.02 넘게 흔든다.
- **골든과 route.py 가 함께 진화했다.** 이 지표는 프롬프트가 아니라 "라우팅
  테이블이 골든에 얼마나 맞는가"를 재고 있을 수 있다.
- `ext_div`·`ext_index` 는 세 arm 모두 낮다. 프롬프트가 아니라 route.py 에
  배당·지수 밸류에이션 경로가 덜 갖춰진 쪽에 가깝다.

## 11. 4차 — 골든 273행 확장과 미노출 표본 148행

골든이 67 → 99(`ext_edge` 32행 신규) → **273행**(`work`/`invest` 각 100행
전량 라벨링)으로 늘었다. 이로써 **적합에 한 번도 쓰인 적 없는 표본 148행**이
확보됐다.

- `ext_edge` 32행 — 최소대립쌍 위주. 그래프·프롬프트 어디에도 노출된 적 없음.
- `work`/`invest` idx 13~99 중 116행 — 파스는 rep1 에 이미 있었으나 **라벨이
  없어 적합에 쓰일 수 없었다.** 추가 API 호출 0회로 측정됐다.

### 결과 — 0.88 이 아니라 0.63

| 구성 | 기존 26행 | ext_edge 32행 | **신규 116행** |
|---|---|---|---|
| A 단일 | 0.9600 | 0.6094 | **0.5887** |
| B 단일 | 0.8947 | 0.6250 | **0.6187** |
| C 단일 | 0.7973 | 0.5137 | 0.5863 |
| A+B+C 다수결 (3콜) | 0.9189 | 0.6327 | **0.6306** |

**독립적인 두 신규 표본이 같은 값을 가리킨다** — ext_edge 0.633, 신규 116행
0.631. 148행이 일관되게 0.62~0.63 이다.

### A 의 우위는 허구였다 — 순위가 뒤집힌다

```
기존  26행:  A 0.9600  >  B 0.8947    (A +0.065)
신규 116행:  A 0.5887  <  B 0.6187    (B +0.030)
```

낙폭이 **A −0.371 > B −0.276 > C −0.211** 로, §2 의 rep1 편향 진단
(A 8/8, B 6/8, C 2/8) 과 순서가 정확히 일치한다. 그래프가 각 arm 에 맞춰진
정도가 곧 낙폭이다. 3차의 "A 채택 철회"에서 한 걸음 더 나가, **B 가 앞선다.**

### 앙상블 이득은 살아남되 미미하다

B 단일 0.6187 → 3콜 앙상블 0.6306 (**+0.012**). ext_edge 에서 +0.008.
§5 의 +0.033 은 적합 데이터에서만 성립하는 값이었다. 3배 비용에 +0.01 이면
채택 여부는 비용 정책이 정할 문제지 성능이 정할 문제가 아니다.

### 실패 양상 — 과호출이 아니라 오식별

호출 **개수**는 잘 맞는다 (ext_edge 골든 평균 1.31 / 예측 1.28, 신규 116행
골든 2.33 / B 예측 2.10). 틀리는 건 **어느 함수인가**다.

```
반도체 업황 뉴스 알려줘            정답 news+sector       예측 news
2차전지 테마 오늘 얼마나 올랐어?     정답 index_price       예측 index_price+sector
코스피200 공매도 잔고              정답 index_shorting     예측 +index_price
현대차 목표주가 얼마야?            정답 eval+financial     예측 eval
```

같은 `get_sector` 가 어떤 행에서는 누락, 다른 행에서는 오호출이다.
`theme→industry channel` 의 발화 조건이 거칠다. 기존 67행에는 이런
최소대립쌍이 없어 드러나지 않았다 — 여러 함수를 다 부르면 대충 맞는
데이터로 적합했더니, 하나만 정확히 골라야 하는 데이터에서 무너졌다.

### 분할 현황

`holdout` 이라는 한 이름이 "아직 안 연 것"과 "열어버린 것"을 뭉뚱그려
소진된 표본을 깨끗한 검증셋으로 착각하게 만들었다. 셋으로 갈랐다.

| 라벨 | 행수 | 의미 |

## 12. 5차 — B 기준 그래프 재적합, 검증 통과

골든이 273행이 되면서 §7 에서 "45행으로는 못 맞춘다"며 기각했던 재적합이
가능해졌다. 기준선은 **B 단일**로 고정했다 — §11 에서 미노출 116행 순위가
뒤집혔고(A 0.5887 < B 0.6187) 낙폭도 A 가 가장 컸다.

- 적합셋 215행 (dev 45 + burned 170)
- 검증셋 58행 (sealed, `work`/`invest` 신규분의 1/3)
- 목적함수: 행별 F1 을 그 행의 B 실행들에 평균낸 뒤 행 단위 매크로 평균
  (한 실행의 우연에 맞추지 않기 위해. 적합셋 행당 평균 2.23 실행)

### 검증 결과 — 근거 두께 순으로 4개 구성을 사전 선언하고 한 번에 열었다

| 구성 | 적합 215 | **SEALED 58** | Δ sealed | 근거 |
|---|---|---|---|---|
| 현행 | 0.7056 | 0.5839 | — | — |
| 최소안 | 0.7190 | 0.6015 | +0.018 | 단독 +0.0065, 발화 12회 |
| **보수안** | 0.7230 | **0.6202** | **+0.036** | + forward 14행 / themed 54회 |
| 전체 재적합 | 0.7306 | 0.6202 | +0.036 | + current **근거 4행** |

**전체 재적합과 보수안이 sealed 에서 완전히 동일하다** — P·R·완전일치까지.
4행짜리 근거의 `("issuer","current") → ("get_stock_news",)` 변경은 적합셋에서
+0.0076 을 벌고 미노출 데이터에서 **정확히 0을 기여했다.** 3차에서 1행 근거를
기각했던 판단이 이번엔 실측으로 확인됐다.

### 채택 — 보수안

```python
JUDGMENT_BUNDLE[("issuer", "forward")] += ("get_stock_news",)
RETIRED = {"comparative assessment", "themed issuer→news channel"}
```

`themed issuer→news channel` 은 테마 엔티티가 있을 때만 종목 뉴스를 붙였다.
그래서 "전망" 질의의 절반을 놓쳤다. 뉴스를 **판단 묶음 쪽으로 옮기니** 조건이
테마 유무가 아니라 판단 여부가 되어 커버리지가 맞아떨어졌다. 단독으로는
그 규칙 제거가 −0.0012 로 해롭고, forward 묶음 변경과 **짝으로만** 이득이다.

`comparative assessment` 는 "업종 평균 대비" 류에 멀티플 두 개를 얹었는데
발화 12회 중 대부분이 오호출이었다. 단독 제거로 sealed +0.018.

두 규칙은 코드에 남기고 `RETIRED` 로 뺐다 — 왜 뺐는지가 다음 라운드에 필요하고,
골든이 더 늘면 되살릴 여지도 있다.

### 이득의 성격

전부 **정밀도**에서 온다. sealed 기준 P 0.597 → 0.678, R 은 0.571 로 불변.
완전일치는 17 → 18/58. 덜 부르게 만든 변경이지 더 잘 맞히게 만든 변경이 아니다.
§11 이 지목한 오식별(`get_sector` 등)은 그대로 남아 있다.

### 남은 상태 — 깨끗한 표본이 0이다

| 라벨 | 행수 |
|---|---|
| `dev` | 45 |
| `burned` | 228 |
| `sealed` | **0** |

이번 검증으로 58행을 소진했다. **다음 개선을 검증할 표본이 없다.** 골든을 더
만들기 전에는 어떤 변경도 "적합셋에서 좋아졌다"까지만 말할 수 있다.

## 13. 6차 — D안(B − intent): 토큰 −14%, F1 +0.015

### 왜 뺐나

B 는 goal 마다 `intent` 코드(I1-1~I9-1)를 낸다. 100% 채워서 나오는데
**`route.py` 는 그 필드를 한 번도 읽지 않는다**(grep 0건). 앞선 측정에서
의도 기반 라우팅은 살릴 이유도 없다는 게 확인됐다.

| | F1 |
|---|---|
| 완벽한 의도 → 택소노미 `대표_함수` 직결 | 0.6821 |
| 완벽한 의도 + `INTENT_MAP` → 그래프 | 0.8424 |
| 완벽한 의도 → 최적 룩업 (LOO, 192행) | 0.8431 |
| 현행 B (goal 분해 → 그래프) | 0.8767 |

의도가 **100% 정확해도** goal 분해보다 낮다. 구조적 이유가 둘이다.

- **같은 intent 조합인데 정답 함수가 다른 경우가 22/48 (46%)** 이다. 라벨이
  같은데 정답이 다르면 어떤 분류기도 어떤 라우터도 가를 수 없다.
- 273행이 129개 intent 조합으로 흩어지고, 그중 **81개는 그 조합을 가진 행이
  하나뿐**이라 예측 자체가 불가능하다.

모델 쪽도 따로 문제는 있다 — B 의 실제 의도 분류는 P 0.828 / **R 0.515** 로
골든이 지목한 의도의 절반을 놓친다. 하지만 그걸 고쳐 도달하는 곳이 0.843 이다.

### 제거 내용과 토큰

`run_csv_d.py` = B 에서 다음을 걷어낸 것.

- 프롬프트 `## STEP 5 — INTENT` 블록 전체 (1,701자, 택소노미 24라벨 + 혼동 가이드)
- 스키마의 `intent` 속성과 `INTENTS` enum
- 출력 CSV 의 `intents` 컬럼

같은 5행에서 실측(B 는 3실행 모두 정확히 6,936):

```
입력 토큰   6,936 → 5,965   (-971, -14.0%)
출력 토큰     341 →   294   (-47)
프롬프트    5,785 → 5,024 tok
```

### 공정 비교 — 각 arm 에 제 그래프를 준다

현행 `route.py` 는 §12 에서 **B 의 파스만 보고** 고른 그래프다. 그걸로 D 를
재면 D 가 불리하다 — A rep1 편향(8/8)과 같은 함정이다. `ab_fit.py` 가 세운
대응대로 네 칸을 다 쟀다 (273행, arm 당 1회 추출).

| 파스 \ 그래프 | 현행(B튜닝) | B자체적합 | D자체적합 |
|---|---|---|---|
| **B** | 0.6998 | **0.7099** | 0.7063 |
| **D** | 0.7080 | 0.7240 | **0.7252** |

```
각자 최적 그래프:  B 0.7099  vs  D 0.7252   Δ +0.0152
현행 그래프에서 :  B 0.6998  vs  D 0.7080   Δ +0.0082
D 가 자기 그래프로 얻는 이득  +0.0171
```

**현행 그래프로만 쟀으면 D 의 우위를 +0.008 로 과소평가했을 것이다.**
실제로는 +0.015 다. B 도 자기 그래프에서 +0.010 을 얻는데(§12 의 적합 조건이
215행·다중 rep 이었고 여기는 273행·단일 rep 이라), 그래프 선택 자체가 조건에
민감하다는 뜻이기도 하다.

각 arm 이 제거한 규칙도 갈린다.

```
B 자체적합 제거:  recommendation bundle, event screening→listing
D 자체적합 제거:  recommendation bundle, market data→index price
```

### 판정

**토큰 −14% 를 쓰면서 F1 이 +0.015 오른다.** "intent 를 뽑느라 하는 분류
사고가 goal 분해에 간접 기여할 수 있다"는 우려는 기각된다. 오히려 STEP 5 가
앞 단계의 분해 판단을 끌어당기고 있었던 쪽에 가깝다.

### 유보 두 가지

- **D 는 1회 추출뿐이다.** B 의 실행 간 SD 는 0.0046 이라 +0.0152 가 잡음에
  묻힐 폭은 아니지만, D 의 분산은 아직 모른다. 이번 세션 초반에 A 가 1회
  추출에서 앞섰다가 반복 측정에서 뒤집힌 전례가 있다. D 를 2~3회 더 돌려야
  확정된다.
- **검증 표본이 없다.** 273행 전부 `burned` 라 위 재적합은 잰 데이터로 맞춘
  것이고 0.7252 도 낙관적이다. 다만 B·D 가 같은 방식으로 낙관적이므로
  차이는 살아남는다.

## 14. 7차 — D 재현성 원인과 프롬프트 절삭·재배치

### D 는 B 와 재현성이 같다

D 를 3회 돌려 B 와 공통 99행에서 짝지어 비교했다.

| arm | 함수 3회동일 | 파스 3회동일 | F1 | SD |
|---|---|---|---|---|
| B | 77/99 | 18/99 | 0.8117 | 0.0154 |
| D | 76/99 | 16/99 | 0.8042 | 0.0171 |

**intent 제거가 재현성을 해치지 않았다.** 다만 §13 의 D 우위(+0.015, 273행)는
여기 99행에서 −0.008 로 뒤집힌다. 채택 근거는 **"토큰 −14% 에 성능 동등"**
까지가 정확하고, "더 낫다"는 표본 의존적이다.

### 재현성을 깎는 것은 goal 분류지 근거 추출이 아니다

273행 × 3회. 파스는 9% 만 완전히 같은데 답(함수 집합)은 67% 가 같다 —
**파스 변동의 대부분이 무해하다.** 그래서 "무엇이 갈리나"가 아니라 "갈렸을 때
답이 바뀌나"로 봐야 한다.

| 단계 | 갈린 행 | 답이 바뀐 행 | 전파율 | 기여도 |
|---|---|---|---|---|
| **goal 분류 (STEP 4)** | 77 | 46 | **60%** | **51%** |
| goal 개수 (STEP 0 근거 인벤토리) | 54 | 27 | 50% | 30% |
| 엔티티 추출 (STEP 2) | 79 | 15 | 19% | 17% |
| horizon (STEP 4) | 4 | 2 | 50% | 2% |
| 제약 추출 (STEP 3) | 10 | 0 | **0%** | 0% |
| 값 문자열만 | 24 | 0 | 0% | 0% |

goal 개수는 80% 의 행에서 안 흔들린다(최대−최소=0). 흔들리는 건 **개수가 같은데
`domain`/`facet`/`type` 을 다르게 붙이는 것**이고, 그게 60% 확률로 답을 바꾼다.

### 절삭 실험 — 세 개 다 기각

프롬프트 5,024 tok 중 STEP 4 가 33%, 경계 예시가 29% 다. enum 미사용 값 삭제
같은 공짜 절감은 없다(정의된 값이 거의 다 실제로 쓰인다).

층화 27행 × 3회:

| 변형 | F1 평균 | SD | Δtok | 판정 |
|---|---|---|---|---|
| **pcls1** — CLASSIFY 를 맨 앞으로 | **0.8404** | **0.0112** | **±0** | **채택** |
| d (기준) | 0.8148 | 0.0241 | — | — |
| cex — 경계 예시 8→4 | 0.7960 | 0.0093 | −571 | 기각 |
| ccon — STEP 3 설명 제거 | 0.8079\* | — | −124 | 기각 |
| cent — STEP 2 설명 제거 | 0.7771\* | — | −281 | 기각 |
| pcls2 — CLASSIFY 를 뒤로 | 0.8005\* | — | ±0 | 기각 |

\* 1회 측정.

```
pcls1 - cex :  +0.0444   9/9 실행쌍 pcls1 우세
d     - pcls1: -0.0256   8/9 실행쌍 pcls1 우세
```

**`cent` 가 가장 크게 떨어졌다.** 스키마가 strict enum 이라 타입 이름은 이미
강제되니 한글 설명이 없어도 될 줄 알았는데 아니었다. `route.py` 가 엔티티
타입으로 팬아웃을 정하므로(`theme→sector`, `product→knowledge`) 타입 판정이
흔들리면 곧바로 답이 바뀐다.

**결론: D 의 5,024 tok 은 대체로 값을 하고 있다.** 남은 절감은 STEP 4 재작성
같은 구조 변경에서만 나온다.

### 채택 — pcls1 (위치 변경, 토큰 ±0)

`## STEP 4 — CLASSIFY` 를 `## STEP 0` 앞으로 옮겼다. 재현성 진단이 지목한
바로 그 블록을 먼저 읽히는 것이고, SD 가 0.0241 → 0.0112 로 절반이 됐다.
토큰 비용이 0 이라 위험이 없다.

**유보**: STEP 번호가 이제 4→0→1→2→3→5→6 으로 읽힌다. `pcls1` 이 이긴 게
"분류를 먼저 읽어서"인지 "번호가 뒤섞여서"인지 이 실험으로는 못 가른다.
번호를 다시 매기면 그건 측정하지 않은 새 변형이므로 손대지 않았다.
